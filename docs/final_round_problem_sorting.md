# 决赛阶段问题与数据接口梳理

## 1. 问题形态变化

初赛阶段的数据是静态表格：每条样本给出完整态势、策略编号以及策略执行后的两个指标，算法目标是在测试样本上推荐离散策略。

决赛阶段的数据形态发生变化：红蓝双方数量保持不变，但蓝方目标位置随时间变化；仿真系统按照单一策略执行，并在指定监控间隔时刻记录实时态势。赛方一个样本目录就是一次仿真、一种策略的结果。CSV 文件名后缀 `_0/_1/_2` 是按时间累积的分段编号，一个文件大约覆盖 100–200 个时间刻。同一时刻可能观测到几十个蓝方实体；时间推进时可能新增观测，也可能因拦截成功从态势中消失。几十个实体里会有若干组成群。另外两种策略格式相同，只是当前样本未复制且没有数值。最终评估时，算法需要在仿真系统触发的当前态势下，实时输出三种既定策略之一。

因此，决赛阶段不再是单纯的“离线表格策略推荐”，而是：

```text
实时态势输入 -> 状态特征抽取 -> 三策略收益/风险估计 -> 输出当前最优策略
```

决策对象仍是离散策略，但输入从静态样本变为动态时刻状态。

## 2. 已知数据表

### 2.1 `Stu_ZZGLRHDL_*`：蓝方目标态势信息

该表记录蓝方目标在监控间隔时刻的态势状态。当前已知字段包括：

| 字段 | 含义 | 建模用途 |
| --- | --- | --- |
| `TargetUnitID` | 目标句柄，目标唯一序号 | 用于跨时刻跟踪同一目标；后续检测不到可视为已被拦截或脱离监控 |
| `TargetUnitName` | 目标名称 | 可作为辅助标识，一般不直接建模 |
| `B_Sgzmb` | 跟踪目标标志位 | 判断目标是否被识别/跟踪到 |
| `B_l_jbz` | 正在拦截目标标志位 | 判断当前是否已有拦截动作指向该目标 |
| `B_Sdk` | 低空标志 | 当前可能需要自行根据高度阈值计算 |
| `B_QMBflag` | 群目标标志位 | 当前可能需要根据目标空间聚集关系自行计算 |
| `Uc_XXYLY` | 目标信息源类型/来源 | 可用于判断探测来源或目标信息可靠性 |
| `Uc_XXYHandle` | 目标信息源句柄 | 可关联红方装备信息表，识别由哪类装备提供目标信息 |
| `D_Bsm` | 群方位覆盖范围 | 可自行计算；若缺数值可暂不作为核心输入 |
| `D_Esm` | 群高低覆盖范围 | 可自行计算；若缺数值可暂不作为核心输入 |
| `Ui_Zwx` | 目标威胁值 | 排序信息，数值越小威胁越大；应按监控时刻重排 |
| `D_XDPm` | 相对保护要点最小航路距离 | 衡量目标接近要害程度 |
| `D_XDTm` | 相对保护要点预计时间 | 衡量目标到达时间压力 |
| `D_XDRm` | 相对保护要点最小斜距 | 衡量空间接近程度 |
| `D_R/D_E/D_B` | 斜距/高低角/方位角 | 目标相对位置特征 |
| `D_RV/D_EV/D_BV` | 斜距/高低角/方位角变化率 | 目标运动趋势，变化率可理解为速度或接近速度分量 |
| `D_X/D_Y/D_Z` | 目标三维位置 | 计算距离、聚类、群中心、分散程度 |
| `D_XV/D_YV/D_ZV` | 目标三维速度 | 计算速度大小、朝向、接近趋势 |
| `FZTime` | 仿真时刻 | 用于构造动态序列状态 |
| `DetectTime` | 探测时刻 | 用于判断目标信息新鲜度 |

关键理解：`TargetUnitID` 是时间序列的连接键。若某目标在后续时刻不再出现，不能简单当作缺失值，而应作为“已被拦截/失去监测”的重要状态变化。

### 2.2 `HealthState_0`：红蓝双方生命状态与装备位置

该表不分段：一次仿真从开始到结束都写在同一个 `HealthState_0.csv` 里。`Stu_ZZGLRHDL_*` 和 `Stu_ZZGLLJ_*` 才按时间刻切成 `_0/_1/_2`。

红方 `HealthPoint` 始终为 1、位置不变，因此红方实体只在 `Time=0` 记一行。蓝方不重复记录持续为 1 的行：同一个实体只记 `HealthPoint=1` 的首次出现时刻，以及变为 `0` 的拦截时刻；中途新观测到的蓝方在首次出现时补一行 1。读取某时刻态势时，按该实体不晚于该时刻的最近一条生命记录回填。

该表记录实体状态，已知字段包括：

| 字段 | 含义 | 建模用途 |
| --- | --- | --- |
| `UnitID` | 实体编号 | 与目标或装备实体关联 |
| `UnitType` | 实体类型 | 区分装备/目标类型 |
| `UnitName` | 实体名称 | 辅助标识 |
| `UnitTeam` | 阵营，红方或蓝方 | 区分防御资源和来袭目标 |
| `UnitPos_x/y/z` | 实体位置 | 计算目标-装备距离、拦截覆盖、资源分布 |
| `UnitPos_lon/lat/alt` | 经纬高 | 可能用于地理坐标场景 |
| `HealthPoint` | 生命值 | 初始为1；蓝方被拦截后为0，无中间态 |
| `Time` | 时刻 | 与态势表按时间对齐 |

关键理解：`HealthPoint` 不是连续毁伤程度，而更接近二值存活状态。蓝方从1变为0可作为拦截成功结果；红方状态可用于判断装备是否仍可用。

### 2.3 `Stu_ZZGLLJ_*`：红方实体对蓝方的可拦截关系

该表记录某个时刻是否有红方实体可以拦截某个蓝方目标。这里没有独立的“火力”层：拦截主体就是红方实体，实体类型只有 4 种。已知字段包括：

| 字段 | 含义 | 建模用途 |
| --- | --- | --- |
| `UI_Targethandle` | 蓝方目标句柄 | 关联目标态势表 |
| `UI_Hlhandle` | 下级单元句柄 | 关联红方拦截实体 |
| `UC_HlType` | 实体类型 | 仅 4 种实体类型 |
| `UI_FSChandle` | 实体/车句柄 | 关联红方装备信息表 |
| `Str_HLMC` | 实体类型/名称 | 识别该实体属于哪一类 |
| `B_DDKsslj` | 该类实体可实施拦截 | 四类实体可拦截标志之一 |
| `B_GPKsslj` | 该类实体可实施拦截 | 四类实体可拦截标志之一 |
| `B_HPMKsslj` | 该类实体可实施拦截 | 四类实体可拦截标志之一 |
| `B_GNJGKsslj` | 该类实体可实施拦截 | 四类实体可拦截标志之一 |
| `B_Kgz` | 可跟踪目标 | 目标是否处于可跟踪范围 |
| `B_Ygz` | 已在下级单元列表中 | 该实体是否已纳入当前拦截单元集合 |
| `B_TD` | 通道约束 | 通道是否满足拦截条件 |
| `G_HLYS` | 剩余实体约束 | 可转化为实体占用/剩余能力 |
| `D_Pm/D_Rm/D_Tmzi` | 航路/斜距/预测遭遇时间 | 衡量拦截窗口和紧迫性 |
| `D_Costgy` | 消耗价值 | 计算效费比和策略成本 |
| `G_LJGL` | 拦截概率 | 已知常见值为 0.7 或 0.9 |
| `Time` | 时刻 | 与态势表、生命状态表对齐 |

接口文档把四个可实施拦截标志写成导弹/高炮/高功率/高能激光，样本说明行写成实体1/实体2/高功率/干扰。后续以赛方实体类型枚举为准，建模时只按“4 类实体能否拦截”处理，不引入火力概念。

关键理解：该表是“红方实体-蓝方目标”匹配图。每一行是一条候选拦截边：

```text
蓝方目标 i -- 可由某个红方实体拦截 --> 拦截概率 p，成本 c，通道/剩余实体约束
```

### 2.4 `Stu_SJZS_0`：策略信息

该表提供样本执行的策略字段：

| 字段 | 含义 |
| --- | --- |
| `S_LJCL` / `LJCL` | 拦截策略编号 |

根据 `集成接口.xlsx`，决赛输出策略为三类：

| 编号 | 策略含义 | 侧重点 |
| --- | --- | --- |
| 1 | 闭合时间最短 | 尽快完成交战/闭合，偏时间紧迫 |
| 2 | 拦截性能最佳 | 偏高拦截概率、高拦截效能 |
| 3 | 综合效益最优 | 权衡拦截收益与消耗成本 |

样本表 `Stu_SJZS_0` 中字段名为 `S_LJCL`（string），接口输出字段名为 `LJCL`（Enum）。

## 3. 集成接口理解（实时评估入口）

`决赛/集成接口.xlsx` 定义的是仿真系统实时触发时的输入输出，比样本 CSV 更精简。

### 3.1 输入：目标相关数据列表

| 字段 | 含义 |
| --- | --- |
| `TargetUnitID` | 目标句柄 |
| `TargetUnitType` | 目标类型 |
| `B_l_jbz` | 正在拦截标志 |
| `Ui_Zwx` | 威胁排序（越小威胁越大） |
| `D_X/D_Y/D_Z` | 位置 |
| `D_XV/D_YV/D_ZV` | 速度/变化率 |
| `Klj_list` | 该目标的可拦截性列表（嵌套） |

说明：实时接口未直接给出 `B_Sdk`、`B_QMBflag`、`D_Bsm`、`D_Esm`、`B_Sgzmb` 等样本表字段；若要用，需自行计算或从历史缓存推断。

### 3.2 输入：可拦截性列表（嵌套于目标或独立列表）

| 字段 | 含义 |
| --- | --- |
| `UI_FSChandle` | 实体句柄 |
| `Str_HLMC` | 实体类型 |
| `B_DDKsslj` | 该类实体可实施拦截 |
| `B_GPKsslj` | 该类实体可实施拦截 |
| `B_HPMKsslj` | 该类实体可实施拦截 |
| `B_GNJGKsslj` | 该类实体可实施拦截 |
| `D_LJGL` | 拦截概率（样本侧为 `G_LJGL`，常见 0.7 / 0.9） |

红方拦截主体就是实体，实体类型只有 4 种；四个布尔字段分别表示对应类型实体此刻能否拦截该目标。

### 3.3 输入：装备相关数据列表

| 字段 | 含义 |
| --- | --- |
| `UnitID` | 实体句柄 |
| `UnitType` | 实体类型 |
| `UnitPos_x/y/z` | 位置 |
| `UnitPos_lon/lat/alt` | 经纬高 |

### 3.4 输出

```text
LJCL ∈ {1, 2, 3}
```

即当前触发态势下推荐执行的策略编号。

## 4. 决赛阶段的核心建模对象

决赛阶段建议把每个触发时刻建模为一个“动态拦截态势图”：

```text
节点：
  蓝方目标节点：位置、速度、威胁排序、是否被跟踪、是否正在被拦截、是否低空、是否群目标
  红方实体节点：位置、实体类型（仅 4 种）、存活状态

边：
  红方实体 -> 蓝方目标：是否可拦截、拦截概率、消耗价值、遭遇时间、通道/剩余实体约束

全局状态：
  当前时刻、剩余目标数、剩余可用装备数、目标群空间分布、威胁集中度、资源饱和度
```

因此，最终算法不是只看单目标，也不是只看装备总量，而是要评估“当前红方资源能否覆盖当前蓝方目标群，以及三种策略在该状态下哪一种更优”。

## 5. 可直接构造的特征

### 5.1 目标态势特征

- 当前存活/被监测目标数；
- 被跟踪目标数；
- 正在被拦截目标数；
- 高威胁目标数，按 `Ui_Zwx` 排序，数值越小威胁越大；
- 目标威胁均值、最小值、分位数；
- 目标位置中心、空间分散度、最大/最小距离；
- 目标速度均值、最大值、接近速度；
- 距离保护要点的最小距离、平均距离；
- 预计到达时间最小值、平均值；
- 低空目标比例；
- 群目标比例或目标群数量。

### 5.2 红方装备资源特征

- 红方存活实体数；
- 4 类实体各自数量；
- 4 类实体各自可拦截目标数；
- 4 类实体平均拦截概率；
- 4 类实体总成本、平均成本；
- 高概率拦截实体数量，如 `G_LJGL=0.9` 的链路数量；
- 低成本拦截实体数量；
- 实体空间覆盖范围和分散度。

### 5.3 资源-目标匹配特征

- 总可拦截链路数；
- 每个目标可用链路数的均值、最小值、最大值；
- 无链路覆盖目标数；
- 高威胁目标的可拦截链路数；
- 每个实体可拦截目标数；
- 通道是否拥塞；
- 资源/目标比；
- 高概率链路覆盖率；
- 低成本链路覆盖率；
- 期望拦截收益：`sum(p)` 或按目标威胁加权的 `sum(w_i * p_ij)`；
- 期望成本：`sum(c)` 或策略候选链路成本；
- 性价比代理：`sum(w_i * p_ij) / sum(c_ij)`。

### 5.4 动态变化特征

如果接口连续触发，可以利用上一时刻状态构造：

- 新出现目标数；
- 消失目标数，可能代表已拦截；
- 目标平均距离变化；
- 威胁排序变化；
- 高威胁目标是否已被拦截；
- 拦截中目标比例变化；
- 可用链路数量变化；
- 红方装备损失变化。

如果评估接口每次只给当前时刻，不给历史缓存，则算法内部应自行维护一个按 `TargetUnitID` 和 `Time` 更新的状态缓存。

## 6. 低空标志、群目标标志和覆盖范围的处理

### 6.1 低空标志

若赛方不给 `B_Sdk` 数值，可根据 `D_Z`、`UnitPos_alt` 或高度字段设置阈值判断。阈值需要等待正式规则或样例数值确定。没有阈值前，低空标志暂不作为强约束，只作为可选特征。

### 6.2 群目标标志

可根据目标间空间距离自行计算，例如：

1. 对当前时刻目标位置做聚类；
2. 若某目标邻域内目标数超过阈值，则标记为群目标；
3. 统计群目标数量、群中心、群半径和群分散度。

若目标数量固定且不大，也可以直接使用目标间平均距离、最近邻距离、空间协方差等连续特征替代硬标志。

### 6.3 群方位覆盖范围与群高低覆盖范围

这两个字段可以通过方位角和高低角的最大值减最小值计算：

```text
群方位覆盖范围 = max(D_B) - min(D_B)
群高低覆盖范围 = max(D_E) - min(D_E)
```

若角度存在跨 0/360 度问题，需要使用圆周角跨度计算。

## 7. 训练数据不足时的策略

目前赛方只给部分格式，没有完整数值数据，因此不能立即训练最终监督模型。此时应先准备三层方案：

1. 数据解析层：能接收接口输入，稳定解析目标、装备、链路、策略字段；
2. 特征抽取层：把实时态势图转化为固定维度特征；
3. 策略选择层：在无标签阶段先使用规则/仿真反馈驱动，在有数据后切换为监督学习或离线强化学习。

## 8. 推荐技术路线

### 8.1 第一阶段：规则启发式基线

在没有完整训练数据时，先构造可解释规则：

- 若高威胁目标多、预计到达时间短、可用链路紧张，则选择偏高拦截率策略；
- 若目标威胁较低、覆盖充足、成本差异明显，则选择偏效费比策略；
- 若目标分散、链路覆盖不均衡，则选择偏综合调度策略。

该规则不一定最终提交，但可作为接口联调和仿真采样的基线。

### 8.2 第二阶段：仿真采样生成训练集

对不同初始位置场景分别执行三种策略，按监控间隔记录：

```text
state_t, strategy, next_state, intercepted_count, cost, terminal_result
```

由此形成策略收益数据。每个状态下三种策略的优劣可以从后续一段时间或整局结果反推。

### 8.3 第三阶段：候选策略收益模型

将三种策略作为候选动作，对每个当前态势 `x_t` 和策略 `s` 预测：

```text
Q(x_t, s) = 拦截收益 - 成本惩罚 - 漏防风险惩罚
```

推荐：

```text
s* = argmax_s Q(x_t, s)
```

这与初赛最终方案一致：不是直接分类历史策略，而是对每个候选策略打分。

### 8.4 第四阶段：Pairwise/排序纠偏

如果同一状态或相似状态下有三种策略执行结果，可继续构造策略对：

```text
(state_t, strategy_a, strategy_b) -> strategy_a 是否优于 strategy_b
```

用于学习策略相对边界，减少某一策略被全局过推荐。

### 8.5 第五阶段：在线状态缓存与实时决策

决赛接口是实时触发，算法需要维护缓存：

- 目标上次出现时刻；
- 目标是否持续被跟踪；
- 目标是否消失；
- 目标速度/威胁变化；
- 已拦截目标数量；
- 红方装备剩余状态。

这样才能把“当前一帧信息”扩展成“动态态势信息”。

## 9. 与初赛算法的继承关系

初赛最终算法中仍可继承的部分：

- 离散策略候选枚举思想；
- 不把历史策略当作唯一标签，而是学习候选策略收益；
- 目标收益排序而不是简单分类；
- 特征工程优先于盲目套模型；
- Pairwise纠偏思想；
- 策略分布偏置诊断。

需要重构的部分：

- 原始42维静态字段不再适用；
- 核心25特征需要改造成动态态势图特征；
- 指标不再直接由表格给出，需要从仿真过程计算；
- 模型训练依赖新增仿真采样数据；
- 推理入口需要按集成接口实时输入输出。

## 10. 当前已落地的构造-训练-推理链路

赛方暂无数值数据，因此本地先用已知格式构造场景，再训练可导出的模型：

1. `python scripts/make_finals_synth_data.py` 生成 `outputs/finals_synth/sample_xxx_s{1,2,3}/`，每个目录等价于赛方「一个样本」：一种策略的一次仿真 CSV 分段（`_0/_1/...` 按 200 个时间刻切分）；
2. `python scripts/build_finals_training_set.py` 整理为固定维特征 + 三策略收益样本；
3. `python scripts/train_finals_model.py` 训练随机森林收益模型 + pairwise 纠偏，导出 `outputs/finals_model/policy.pkl`；
4. 实时入口 `submission_finals/recommend.py`：当前态势 -> `LJCL ∈ {1,2,3}`。

一键：`python scripts/run_finals_pipeline.py`

赛方电脑上若换成真实同格式 CSV，只需改 `--input` 重训，推理接口不变。低空、群目标、覆盖范围在特征层自算。
